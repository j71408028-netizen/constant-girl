# 副本角色系统：人物表与运行期账本（面向作者）

> **这一篇回答什么问题**：方案里怎么写「这个故事里有谁」——主角、配角、群像各填哪些字段；以及一局跑起来之后，程序怎么记住「谁在场、这个称呼是谁、他什么时候露了真名」。**写方案的作者**看 §1～§3；**想知道 AI 为什么这么写人**的看 §4～§6；**想知道在哪看人、在哪改代码**的看 §7 界面与 §8 内部实现。
>
> 相关页面：章节与触发器的完整字段索引 [script.md](script.md) · 谁用什么嗓子朗读 [voice.md](voice.md) · 编辑器里的「角色」页 [../scenario_editor.md](../scenario_editor.md) · 人物带来的演化量 [../character_evolution.md](../character_evolution.md)。
>
> 字段声明的单一真相源是方案的 schema；本篇是字段与机制的权威说明，改代码时两边要同步。

## 1. 四种角色，各存在哪

角色系统分四个平面（数据 / 提示词 / 语音 / 数值），共用一套身份，但不共用存储。先认清四种「角色」在数据里的位置，后面所有规则都从这里长出来：

| 角色 | 存在哪 | 说明 |
|---|---|---|
| 她 | 本局角色档案 | 名字 / 性格 / 身高 / 部位；跨方案复用，不属于方案 |
| 主角 | `protagonist_title` + `protagonist_background` | 唯一、视角固定，**不进人物表** |
| 配角 | `cast[]` | `key` 有完整身份背景，`extra` 只有三条线索 |
| 环境 | 无实体 | 只是演化量的一个归属档（`owner`） |

**所有描述都是故事开始时的样子，不是状态**：谁死了、谁反目了，不改配置——那是这一局的摘要事实。本局的身份状态、当前称呼、特征与关系由运行期账本持有，不回写配置。三条边界守住了这个分工：

1. **她不在方案里，主角不进 `cast[]`**——否则「谁是主角」就有两处真相，渲染还得开特例；
2. **在场以章节 `cast` 声明为主来源**，账本的观测只是补充，而且不进「本段在场」那一行；
3. **账本只被读、不被提示词构建写**——所有写入只走「回合提交」（§8）或后台抽取（§6）。

## 2. 主角怎么写

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `protagonist_title` | str | `""` | 称呼（`tagged` 记法下 `@说话人@` 标注用），留空回退「主角」；`literary` 下不作说话人标注 |
| `protagonist_background` | text | `""` | 身份背景：他是谁、为什么在这儿、想要什么、怎么看她。**不写身高**，身高由角色快照注入 |

`protagonist_background` 非空时，系统提示词的设定区（`initial_prompt` 之前）会多一块；有角色快照（身高 > 0）时，块里多一行身高：

```
【主角】指挥官
身高：1001米
故事开始时：外地调来的救援调度员，任务是把东岸居民撤完；既指望她开路，又怕她失控。
（以上是起点不是现状，不必每段重述。）
```

身高行取自角色快照（`body_parts["身高"]`，缺失时退到 `height`），**方案文案里不要写死**：同一份方案会被不同身材的角色使用，写死的身高会与快照、与尺度换算行互相矛盾。

这块内容随系统提示词每段都在（主角是视角人物，「他是谁」与她的性格描述同级），变的是处境，走摘要事实。也正因为每段都在，文案必须点明「这是起点」——否则 AI 会把它当成每段都要维持的现状。

## 3. 人物表怎么写

`cast[]` 里每个成员是 `key`（重要角色）或 `extra`（群像），两档能填的字段不一样：

| 字段 | 类型 | 默认 | 哪档用 | 说明 |
|---|---|---|---|---|
| `id` | str | 同 `name` | 两档 | 标识；章节 `cast` 与别称解析都用它 |
| `role` | enum | `key` | — | `key` 重要角色（有完整背景）/ `extra` 群像 |
| `name` | str | — | 两档 | 称呼（必填）；**永远填真名 / 正式称呼**，也是说话人解析与音色匹配的最终键 |
| `intro_as` | str | `""` | `key` | 真名揭示前对外的**临时称呼**；空 = 开局即用 `name`。非空时开局处于「临时」状态，渲染与说话人匹配优先用它 |
| `pronoun` | enum | `""` | 两档 | `他` / `她` / 空；参与渲染与音色分池，空 = 不猜 |
| `voice` | str | `""` | 两档 | 显式音色；空 = 按 `pronoun` 落到音色池 |
| `background` | text | `""` | `key` | 完整描述 |
| `aliases` | list | `[]` | `key` | 别称：让 `@李队@` 与 `@李队长@` 归到同一人、同一把嗓子 |
| `call_her` | str | `""` | `key` | 他怎么称呼她 |
| `purpose` | str | `""` | `extra` | 作用：为什么要有这个角色 |
| `speech` | str | `""` | `extra` | 说话方式 |

两档**各自只有一条「他是谁」的线索**，这是字段按档位分家的理由：

- **重要角色只要 `background`**。背景写清了，「说话是什么样」自然从人设里长出来；再给一栏 `speech`，你会把同一件事写两遍，而 AI 拿到两份措辞不同的描述。
- **群像没有 `background`**，才需要 `purpose`（他为什么在这个故事里）与 `speech`（他听起来什么样）两条线索。
- `aliases` / `call_her` 只属于重要角色：它们是喂给说话人解析与称呼渲染的**结构化线索**，而群像活得短、名字就是唯一标识，不值得再维护一套称呼。

这条归属在代码里就是 `dungeon/cast.py::role_supports`，渲染与角色页都问它。

章节用 `cast` 声明谁在场：

```json
{ "name": "第三幕", "cast": ["李队长", "王店主"] }
```

写 id / 称呼 / 别称都认（`@` 会被剥掉）。归一化时按 `、,，;；空白` 切分、去 `@`、去重；**没写就不补键**，旧磁盘内容一字不变。章节 `cast` 是**唯一**的在场来源——这一点决定 §4 里「不在场的人一个字都不进提示词」。

<details>
<summary>人物表校验口径（写完方案看这里，报错信息对不上时也看这里）</summary>

| 级别 | 条件 |
|---|---|
| error | 成员缺 `name`；`id` 重复；称呼 / 别称与另一个成员撞车；`intro_as` 与成员称呼 / 主角称呼撞车（都会让说话人与音色串台） |
| warning | `role` / `pronoun` 取值非法；章节 `cast` 指向不存在的成员；描述字段超长 |
| info | `key` 成员超过 6 个；`key` 没填 `background`（首次出场只会给出称呼） |

完整校验器口径见[数据模型 §9](script.md)。编辑器在存盘前会先拦一遍，别等运行时才发现撞名。

## 4. 提示词里会出现什么

| 内容 | 位置 | 频率 |
|---|---|---|
| 主角设定 | 系统提示词设定区 | 每段（基底） |
| 本章在场行 | 用户提示词「当前地点」之后 | 章节 `cast` 非空时每段 |
| 配角设定块 | 同在用户提示词，紧跟在场行 | **首次出场一次** |
| 人物简报 | 首次出场块之后 | 已出场的在场成员**每段** |

**没在本章 `cast` 里声明的成员，一个字都不进提示词**——这同时解决了「AI 把每个人都写进每一段」的老毛病：不在场的人根本不在提示词里。这条对对话、分支、行动、背景一类段落一视同仁。

首次出场时，填了线索的成员渲染成设定行；三条线索全空的成员给一条「由 AI 定」的指令：

```
【本段首次出场】赵司机
你需要在这一段让上述角色自然出场，并确定三件事：他们为什么在这个故事里、
各自的代词、各自的说话方式。确定之后保持前后一致。
（以上是起点不是现状，不必每段重述。）
```

AI 定的线索**不回写配置**：方案要跨局复用，写回会让下一局顶着上一局的设定开场；需要跨段保留的身份状态进本局账本（§5）。

首次出场之后，在场成员改走**人物简报**：重要角色给身份首句 + 称她为 + 可变状态（特征 / 关系），群像给作用 + 说话方式。完整设定块会随对话窗口滑出去，简报负责让「他是谁」不随窗口消失；它只包含本章 `cast` 声明的在场者，不会每段把整张人物表重发一遍。

**说话人规则**（仅 `tagged` 记法且有角色时追加）：未知名第一次说话时，用正文里已经出现的稳定临时称呼做标记、不要每段换叫法；真名揭示后一律用真名；一个角色一段只有一个标记。`literary` 记法与空配置都不追加，逐字不变。

## 5. 一局里的身份：怎么认人、怎么揭示

账本把每个成员分三层存：`initial`（方案成员的只读副本）、`mutable`（身份状态：状态 / 当前称呼 / 真名 / 别称 / 特征 / 关系）、`observed`（在场观测：是否在场、最近见过的段与章、在哪、首次出现、音色键）。**群像只有初始与观测两层**——不积累特征、不参与身份揭示，简报每段按初始字段重新渲染。AI 现编的角色以重要角色登记，初始只有名字。

**身份状态机**：

```
未知 ──首次被观测到（@说话人@ / AI 声明 / 临时称呼）──▶ 临时
临时 ──真名被揭示（正文锚点 / 手动确认）──▶ 已揭示
已揭示 ──不回退；改名只追加别称──▶ 已揭示
```

- 没有 `intro_as` 的成员开局即「已揭示」（真名 = `name`），行为与旧版一致；
- 有 `intro_as` 的开局「临时」，对外用临时称呼，真名等剧情揭示；
- 揭示后旧称呼进别称（上限 6 个），说话人标记与语音都改跟真名。

**在场观测**有三个来源，优先级从高到低：

1. **章节声明**：本章 `cast` 里的人直接算在场；
2. **说话人标记**：`@X@` 出现时，未知称呼登记成 AI 现编角色；连续两段出现升级为在场，否则只是被提起；
3. **正文点名**：已知角色的任一称呼出现在正文里，记为被提起。

连续两段没再出现的人会被标成缺席（保留「最近见过」供「最近离开」列表用）。观测**只升级不降级**：迟到的后台结果（段号更小）不回退；同一段里先被点名、又开口说话，升级为在场。注意：**本章 `cast` 没声明的人即使被观测到在场，也不进「本段在场」行**，只会出现在「AI 现编且在场」的补充简报里。

**揭示与合并**是最保守的一环：真名揭示要求正文里同时出现旧称呼与真名两个锚点；AI 只给判断、正文找不到锚点的记进待确认，不自动生效。两个设定成员之间**永不自动合并**，撞车只登记待确认。合并等于源并入目标（别称取并集、特征取并集、观测取较新、目标转为已揭示），每次都写一条合并日志（上限 50 条），方便事后查「是不是认错人了」。抽取失败或 JSON 坏掉时账本不变，简报仍可用确定性字段渲染，不弹窗。

**容量与快照**：重要角色上限 24 个，满了先淘汰「不在场 + AI 现编」里最久没见的，设定成员永不淘汰；特征每人 4 条 × 40 字，单条简报总长 600 字（超限降级成「名字一行」）。整本账本（含待确认与合并日志）随回放落盘，回放头部整本还原为只读视图；旧回放没有快照，保持原来的种子结果。

## 6. 状态从哪来，语音怎么分

状态有三条通道，**AI 不是唯一来源**：

| 通道 | 触发 | 落点 |
|---|---|---|
| 确定性 | `@X@` 解析、章节 `cast`、`intro_as`、说话人规则 | 不需要 AI |
| 细节探究搭车 | 每章一次的后台细节调用返回角色更新 | 应用到账本 |
| 摘要搭车 | 压缩响应里带角色更新 | 应用到账本 |

两条 AI 通道都是**既有调用的搭车**，不增加调用次数；解析失败返回空列表，不影响主流程。细节探究按章降频之后，这条通道跟着章节走而不是跟着段落走；逐段的在场 / 被提起仍由确定性通道记账，真名揭示与关系变化由压缩搭车（默认每 20 段）与换章压缩补上。应用更新时：未知称呼首次出现登记成临时角色，真名揭示走 §5 的锚点规则，特征 / 关系有界去重，群像不吸收任何可变状态。

**语音分嗓子**按这个顺序解析：她的名字 / 昵称 → 主角称呼 → 账本命中（显式音色优先，没填就按代词过滤音色池后取稳定哈希）→ 其余角色走全池哈希。

关键在**稳定哈希键**：设定成员登记时就是真名，AI 现编角色是第一个称呼——所以临时称呼揭示成真名**不换嗓子**，同一个角色的不同别称也稳定。代词过滤只是在内置音色表里筛一层，不拆两个池；`pronoun` 为空就不过滤。哈希用的是 `crc32` 而不是 Python 的 `hash()`（后者对字符串随机化，重启进程会全体换嗓子）。方案级音色配置、合成与代理的说明见[副本对话语音](voice.md)。

## 7. 两处界面

| 态 | 位置 | 内容 |
|---|---|---|
| 作者态 | 方案编辑器「角色」页 | 她 / 主角 / 人物表卡片 + 音色 + 演化量归属；重要角色卡片有「临时称呼」一行 |
| 运行态 | 副本窗口「人物档案」覆盖层（C 键 / 工具条） | 只读为主：在场 / 最近离开两档，展开看别名 / 特征 / 关系 / 首次出场；对 AI 认错人可以**手动合并** |

运行态不提供编辑设定的入口——方案跨局复用，运行期改设定会污染下一局。结局回顾会把已揭示的重要角色快照（真名 + 别称 + 特征 + 关系）写进结局索引，临时称呼与群像不进；回放路径只读快照，不触发抽取、不写账本。

## 8. 内部实现

- **构建与提交分离**：回合构建是纯函数——不写「已出场」标记、不写账本、不发细节探究。这些副作用装进回合的待提交项，回合成功后再统一提交；预生成失败直接丢弃产物，不需要快照还原。写进对话历史的用户回合只保留章节 / 地点与叙事指令，在场行与简报由下一轮提示词重新渲染，不留在历史里变成过期现状。
- **归一化与只读边界**：缺省键在读取时归一化，旧磁盘内容一字不变；回放路径拦截一切账本写入。

## 9. 拓展用法

- **章节 `cast` 写 id、称呼、别称都认**：同一个人在不同章可以用不同写法（`李队` / `李队长` / `cast_li`），不必统一——只是别在同一章里既写临时称呼又写真名，那会让 AI 以为这是两个人。
- **AI 现编的角色也会进账本**：临时角色在人物档案里和设定成员并列出现，认错人时手动合并一次即可，不用回头改方案。想让某个临时角色长期存在，可以在方案里补一张同名 `key` 卡片——下一局开局它就是个设定成员。

## 10. 作者须知

**兼容红线**（改实现时不能破的约定）：

1. **空配置零差异**：`cast: []` 且没有主角背景时，系统 / 用户提示词逐字不变；
2. **不回写配置**：账本的一切只随局销毁；缺省键读取时归一化，旧磁盘内容一字不变；
3. **旧响应兼容**：细节 / 摘要响应没有新键时行为不变；
4. **回放只读**：回放路径拦截一切账本写入。

**自检**：`python tests/check_characters.py`（账本：种子 / 状态机 / 合并 / 容量 / 简报 / 在场观测 / 快照还原）、`python tests/check_cast.py`（人物表与提示词：空配置零差异、构建 / 提交分离、历史净化、字段归属与撞车校验）。两者都在 `tests/run_checks.py` 的离线集合里。
