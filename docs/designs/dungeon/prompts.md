# 副本提示词：AI 每一段看到什么（面向作者）

> **这一篇回答什么问题**：一局副本里，AI 每一步到底收到了哪些文字、这些文字从方案的
> 哪个字段来、什么会随剧情变化、什么从头到尾不变。改提示词、调人设、抱怨「AI 老忘事」
> 或「她突然不像她了」，答案都在这里。
> - **想让 AI 记住某种设定 / 语气**：§2 系统提示（每段都在）与 §4 上下文（会滑出窗口）。
> - **AI 不认识我写的人物**：§5 人物注入，先确认人物表与章节 `cast` 有没有对齐。
> - **嫌 AI 反复写同一条线索**：§6 细节探究的注入闸门。
> - **查字段与常量**：§11 参数表；**踩坑与契约**：§13 作者须知。
>
> 相关页面：章节字段 [script.md](script.md) · 人物表与账本 [characters.md](characters.md) ·
> 地点与尺寸换算 [scene.md](scene.md) · 对话语音 [voice.md](voice.md)。

提示词不是一份模板，而是**每次生成现拼的一段文字**：系统提示开局定一次，用户提示
每段重算一次，历史消息按窗口裁剪。理解这三层，才知道改哪里有效、改哪里会被冲掉。

## 1. 一次生成的整体形状

一条请求只有三段：

1. **系统提示**（`system`）：她的名字与性格、你在方案里写的故事基调、主角是谁、输出
   协议。**开局构建一次**，整局不变。
2. **对话历史**：最近若干个回合的原文，按窗口裁剪（§4）。
3. **本段用户提示**：此刻的章节、地点、在场人物、坐标、尺度换算、细节补充，以及
   「这一段该写成什么类型」（§3）。**只属于这一次请求**。

模型被要求只回一个 JSON：

```json
{"text": "叙述正文", "direction": 1, "custom_directions": {"狂气": 1}}
```

`text` 是正文；`direction` 是这一段对她顺不顺（-1 / 0 / 1），只影响演化方向，不影响
内容深浅；`custom_directions` 是你声明的每个自定义属性的变化方向。程序先按流式把
`text` 抽出来逐句上屏，再在收尾时解析整块 JSON——格式跑偏不会让整段消失，但会丢掉
`direction` 与自定义属性的那一步。

## 2. 系统提示：开局定一次

系统提示按固定顺序拼成，全部来自方案级字段与**耦合等级**（`coupling_level`）：

| 顺序 | 内容 | 来源 |
|---|---|---|
| 1 | 身份与职责（叙事作家 / 任务叙事 / 个体互动） | 耦合等级内置文案 |
| 2 | `性格描述：…` | 角色快照里的性格 |
| 3 | `身高：…约等于 X 高度的 n 倍` | 角色身材 + 本章地标池（没有可用地标时不出现） |
| 4 | 收集职责与视角约束 | 耦合等级内置文案 |
| 5 | 输出总则（100 字左右、一到三句、叙述为主） | 内置 |
| 6 | 说话人写法声明（`@说话人@` / 自由文学） | 方案 `speaker_notation` |
| 7 | `direction` 与 `custom_directions` 的语义与 JSON 模板 | 内置 + 你的自定义属性名 |
| 8 | 自定义属性的归属提示（`狂气（归属：她）`） | `evolution_attrs[].owner`，写了才出现 |
| 9 | 【主角】称呼 / 身高 / `故事开始时：…` | `protagonist_title`、`protagonist_background` |
| 10 | `故事基调与设定：…` | `initial_prompt` + `section_prompts["global"]` |

耦合等级决定的不只是措辞，还有**职责**：Velum 让 AI 收集「环境、人群、因果、她身上的
变化」并接受跳读请求；Solea 让它收集任务目标、进展、阻碍与各方态度，视角留在主角
一侧；Bulla 让它收集她的念头、情绪、意图与注意力，并强调「被指引不等于服从」。
同一段剧情换一档，写出来的东西会换一个立场。

> **系统提示里没有坐标、没有在场行、没有当前地点**。这些每段都在变，写进系统提示
> 只会让 AI 一直以为开局的状态还成立——它们全部放在用户提示里（§3）。

`initial_prompt` 与 `section_prompts` 的其余键见 §11；带 `（面向作者）` 的字段写法在
[script.md](script.md) 与 [characters.md](characters.md)。

## 3. 本段的用户提示：每段重算

每段按下面的顺序现拼，前一块是「她还记得什么」，中间是「现在是什么状况」，最后是
「这一段要写成什么」：

1. **剧情概要块**：压缩过的历史 + 关键事实 + 关键事件（§4）；还没有概要时退回最近
   三段标题式摘录。
2. **当前章节行**：`当前章节：X（备注）`；章节写了 `place`（或能解析出取景地址）时，
   再加一行 `当前地点：…`。
3. **人物块**：在场行、首次出场设定、人物简报（§5）。
4. **校准块**：`当前坐标：介入度 …（n 级：…）/ 破坏性 …`、两级谓词、尺度句，末句是
   「本段只发生一件与此级别相称的事」（§7）。
5. **细节补充块**：本章提问过的线索里，刚写完那段真的提到了的，才出现在这里（§6）。
6. **段落指令**：`请继续叙述…{instruction}`，`instruction` 是当前段落类型在该耦合
   等级下的写法要求（环境 / 分支 / 对话 / 互动 / 行动五选一；结束章节统一替换为「结局
   段落」的写法）。
7. **输出要求句**：`请严格按系统提示的 JSON 格式输出…`。
8. **参考信息**（有才出现）：上一段提到的身体部位尺寸、她与独特地标「同时在场」的
   对比、刚才选中的选项。
9. **记法细则**：`tagged` 方案在对话段与分支段追加 `@说话人@` 的格式规则；有人物表时
   再加一条「同一角色固定一个称呼」。
10. **高亮规则**：要求它把需要强调的一句用 `==` 包起来（结束章节不追加）。
11. **下一段的固定内容预告**：有延迟插入时，告诉它下一段会插什么、本段只做铺垫。
12. **选项走向**：玩家刚选了选项时，把那条选项的提示带进来。

**只有第 2 步和第 6 步会写进对话历史**。第 1、3、4、5、8–12 步是这一回合的现场快照，
留在历史里会被下一轮当成仍然成立的现状——所以历史里的用户消息只有章节行、指令与
输出要求句。

## 4. 上下文怎么攒：历史窗口与剧情压缩

AI 的记忆由两套机制拼起来，谁也不替代谁：

| 机制 | 装什么 | 容量 | 会不会滑出 |
|---|---|---|---|
| 对话历史 | 最近若干回合的**原文**（用户消息 + 规范 JSON 的助手消息） | 默认 20 条消息 ≈ 10 个回合（`story_recent_count`，2~200） | 会，超出直接丢掉最旧的 |
| 剧情压缩 | 每 20 段压成一条**概要**，另有事实卡与关键事件 | 概要按块累计；事实 12 条、关键事件 12 条（各 ≤60 字） | 不滑出，但事实与事件超出上限时丢最旧 |

压缩的时机是三个：缓冲满 20 段压一块；离开章节时把本章余量强制压掉（不满一块也压）；
生成结局前再压一次。压缩优先交给 AI（温度 0.3，要求回 `{"summary", "facts", …}`），
AI 不可用或返回不合规时退回内部算法——首句 + 高频词 + 末句，保证提示词里永远有概要。

> 回放不调用 AI 压缩，走内部算法；概要只存内存，**不写进回放文件**，回放时按同样的块
> 大小重新累计。

`故事基调与设定` 里写的东西每段都在；`note` 里的东西也每段都在（作为章节备注）；
而**正文说过的话**只有进了概要或还在窗口里才留得住。这条差别决定了设定该写在哪：
长期有效的人设与规则写系统提示，只对这一章成立的氛围写 `note`，一次性的演出写正文。

## 5. 人物怎么进提示词

人物分两条通道：你写在人物表里的**设定**，和运行期账本里的**状态**。

1. **在场行**只认章节 `cast`：`【本段在场】A、B`。章节没声明 `cast`，这一行整行不出现
   ——旧方案逐字不变，AI 自己决定谁在场。
2. **首次出场**给全量：人物表里填了的身份背景、称她为什么、关系，整段给出；没填的
   成员只给名字，并要求 AI 当场确定「为什么在这个故事里、代词、说话方式」三件事。
   每局每个成员只给一次，跨章也不重复。
3. **之后再出场**只给简报（≤600 字）：名字、定位、关系、近况；超长时压缩成「名字 +
   在场」。
4. **AI 现编的角色**只进简报，不进在场行——它们不属于你的方案，程序不替它们作主。
5. 人物块最后固定一句：`本段只让主角与到场的角色说话和行动；未到场者可以被人提起，
   但不要给台词。`

`tagged` 方案下，说话人标记同时是语音与账本的入口：`@李队长@“…”` 会被解析成结构化
说话人，决定这一句念不念、念谁的音色、账本记谁出场。`literary` 方案不写标记，对话
融在叙述里，AI 段落也就没有逐句说话人（名牌与朗读自然安静）。两种写法方案内不许
混用，校验器会把 `literary` 方案里的 `@说话人@` 报成 error。

人物表的字段与账本细节见 [characters.md](characters.md)。

## 6. 细节探究：每章问一次，提到才给

正文写到本章第一段之后，程序会在后台问 AI 一次：「这一章接下来还有什么线索没交代
清楚？」最多收两组「对象 + 方面」。方面只能从八项白名单里选：目的、后果、背景、形态、
关系、位置、进展、条件；对象必须**逐字出现在提问时给它看过的那段正文、近期剧情或长期
记忆里**，代词与虚词一律丢弃。

拿到线索后并不是每段都塞。之后每段生成前，程序看**刚写完的那一段**有没有提到这条
线索的对象：

- 提到了 → 去回放原文与长期记忆里找最相关的一段，按三档注入 `原文参考` / `仅提及` /
  `未记载`；
- 没提到 → 这一段完全不出现；
- 同一条线索一章内最多注入 2 次，整章最多同时挂着 2 条。

`形态` 这一类线索有额外限制：找不到记载时只允许「以既有尺度信息为准」，**不许补写
尺寸与外形**——尺度是角色的真数据，不能让模型现编。

换章即作废：上一章问过的线索、注入计数与「问过」标记一起清空，新章第一段写完再问
一次。提问失败（网络抖动）时不算问过，下一次生成会再试一次。

> 这一次调用还搭车抽取角色更新（新出现的临时称呼、真名揭示、态度变化），不额外发
> 请求。摘要压缩时也会搭车一次，两条通道都只是后台增益，失败不影响正文。

## 7. 尺寸与坐标校准

副本里的「她有多大」不靠正文自由发挥，靠三条注入：

1. **尺度句**：`她的身高 …，约等于 X 高度的 n 倍`（独特地标）或 `相当于 X 的高度`
   （常见地标）。候选池来自本章 `scene_landmarks` 与 `common_private_name` 过滤后的
   常见地标；什么都没配的章节没有换算句，系统提示与校准块都只写身高。
2. **部位尺寸**：上一段正文提到某个部位（步长、腿长、手掌长度、指纹宽度等 15 项），
   下一段就带一条该部位的尺寸对比，并把这一句写进该部位的解锁记录。同一个部位每局
   只提示一次。
3. **同时在场地标**：最近一两段里她的名字（或「她」）与某个独特地标的名字同段或邻段
   出现，就给一条 `她的身高 …，约等于 X 高度的 n 倍`；上一段刚提示过的同一个地标不会
   连着再来一次。

坐标校准块每段都在，写的是**数值 + 级别名 + 这一级的谓词 + 还没到的下一级**，末句
限定「本段只发生一件与此级别相称的事」。它放在用户提示而不是系统提示，就是为了跟着
每一步的坐标走；`direction` 只决定往哪边演化，不决定写多大。

地标与地址的写法见 [scene.md](scene.md)。

## 8. 方案之外的四种调用

除了正文，方案跑起来还会触发四次独立的模型调用。它们各有自己的系统提示，都按耦合
等级取用，都不进对话历史：

| 调用 | 什么时候 | 输出要求 | 温度 |
|---|---|---|---|
| 选项文字 | 选项触发器弹出前，为**没有写 `text` 的选项**各生成一句 | ≤20 字，无解释、无引号、无序号；界面超过 28 字截断 | 0.9 |
| 结局正文 | 结束章节段落数用尽 | 100~300 字叙述文，直接给正文，不要 JSON | 0.9 |
| 剧情概要 | 每 20 段 / 换章 / 结局前 | `{"summary", "facts", "character_updates"}`，概要 ≤100 字 | 0.3 |
| 细节线索 | 每章第一段之后 | `{"queries": [{"object", "aspect"}], "characters": [...]}` | 0.5 |

结局的上下文是状态行（介入度 / 破坏性 / 总伤亡 / 自定义属性）+ 压缩概要（缺失时退回
最近片段）+ 性格描述；AI 客户端不可用时只显示「结局：{名字}」，不拖垮收尾。选项文字
生成失败时退回选项自己的 `prompt`。

固定文本章节（章节配了 `fixed_text`）不发起正文生成、不做细节探究、不做预生成——那
一章的文字是你写好的，AI 只在之后的 AI 章节接着读历史。见 [script.md](script.md) §2.5。

## 9. 内部实现：构建、提交与容错

提示词由副本窗口自己持有的构建器产出，会话对象本身就是它的上下文（名字、性格、身材、
章节、账本、坐标、设置都在上面）。构建分两步：

- **构建**只读不写：产出请求正文、要写进历史的精简版用户消息，以及一份「待提交副作用」
  （本段提示了哪些部位、哪些成员首次出场、哪些线索注入过、哪个地标提示过）。
- **提交**在回合成功后才执行：预生成失败、响应作废、空响应重试，都不会提前消费掉
  「首次出场」或「这条线索已经给过」。

**预生成**：下一次点击必然触发生成时（无选项、无插入、无结局待生成），后台提前发一条
同样的请求；预生成会等本章的细节提问落地（最多 8 秒），等不到就按现有上下文走。换章
立即作废预生成——旧段落是按上一章的环境写的。

**容错**：

- 响应被包在 ```json 代码块里、前后带解释文字，都能取到正文；`direction` 越界按 0；
  `custom_directions` 里不属于方案声明的键直接丢弃，值夹到 -1/0/1；
- 整块不是 JSON 时尽力抽 `text`，连 `text` 都没有就把原文当正文，`direction` 记 0；
- 完全空响应重试一次；仍为空则撤回这一段（不推进步数、不写回放、不判定触发器），
  让玩家再点一次；
- `literary` 方案里模型偶尔串味写出的 `@说话人@`，在进入分句器之前就剥掉，落盘、历史、
  回放一律用归一后的正文。

## 10. 拓展用法

界面上没有明说、但方案数据本身支持的用法：

- **把 `note` 当持续提示用**：章节备注以「当前章节：X（备注）」每段进提示词。写一句
  这一章的氛围或禁忌，比塞进正文可靠——正文会被窗口裁掉，备注不会。
- **把长期禁令写进 `initial_prompt`**：系统提示每段都在，适合写「她始终不会主动伤人」
  这类整局成立的规则；写进章节备注的只在这一章生效。
- **给自定义属性写 `owner`**：`evolution_attrs` 里写了归属，系统提示会多一句「这些自
  定义属性的归属：…；方向描述的是归属方身上的变化」，AI 才知道这一路变化是谁身上的。
- **手写 `section_prompts.global`**：编辑器保存的五个分类键目前不参与提示词（见 §13），
  但 JSON 里手写一个 `global` 键会被并进「故事基调与设定」，可以在不改方案正文的前提下
  追加一段全局口径。
- **人物留空让 AI 现编**：人物表里只写称呼、不写背景，首次出场时它会自己定「为什么在
  这个故事里、代词、说话方式」，之后按简报保持一致。适合群像与路人。
- **章节 `cast` 留空**：整行在场声明不出现，AI 按剧情自由决定谁在场；想收紧阵容再填。
- **复制方案换耦合等级**：同一份章节与触发器，复制成三个方案分别选 Velum / Solea /
  Bulla，可以直接对比三种视角下同一段剧情的写法差异。
- **用 `place` 给「真城市」语境**：写了地点的章节会带一行 `当前地点：…`，模型知道地名
  才写得相称；虚构副本不写，这一行就不出现。
- **手改 `data/user/dungeon_settings.json` 的 `story_recent_count`**：界面上没有这个
  滑条，但它是玩家数据文件里的普通键（2~200）。调大能让 AI 逐字看到更多近期原文，
  代价是 prefill 变长、首字更慢；调小则更依赖剧情压缩。

## 11. 参数表

### 11.1 方案里跟提示词有关的字段

| 字段 | 作用 | 建议 |
|---|---|---|
| `initial_prompt` | 故事基调与设定，进系统提示的最后一节 | 写整局成立的世界观与人设，不写数值身高 |
| `section_prompts` | 五个分类键 + `global`；目前只有 `global` 生效（§13） | 追加全局口径时手写 `global` |
| `coupling_level` | 玩家身份与 AI 职责，决定系统提示与全部副产物提示 | `velum` / `solea` / `bulla`，缺省 `velum` |
| `speaker_notation` | 正文怎么写对话，决定是否追加 `@说话人@` 规则 | `tagged`（默认）/ `literary`，不许混用 |
| `protagonist_title` | 主角称呼，进【主角】块与说话人写法 | 留空回退「主角」 |
| `protagonist_background` | 主角故事开始时的样子，≤300 字 | 写起点，不写现状 |
| `cast[]` | 人物表：首次出场全量、之后简报 | 身份背景 ≤200 字；作用 / 说话方式 ≤60 字 |
| `evolution_attrs[].owner` | 自定义属性的归属，进系统提示 | `her` / `protagonist` / `environment` / `other` |
| `chapters[].note` | 每段进提示词的章节备注 | 一句氛围或禁忌 |
| `chapters[].place` | `当前地点：…` 的显示名 | 留空退回紧凑地址，再空则不出现 |
| `chapters[].cast` | 在场行与首次出场的依据 | 填人物表里的 id / 称呼 / 别称 |

## 13. 作者须知

- **现状：五个段落分类提示不参与提示词。** 编辑器「段落分类提示」的 background /
  branch / dialog / interaction / action 五个框会存进配置，但运行时每个段落类型的写法
  要求取自耦合等级的内置文案；只有 `section_prompts["global"]` 会被并进「故事基调与
  设定」，而编辑器不写这个键（手改 JSON 才有）。想让某类段落换写法，目前只能切方案的
  `coupling_level`——三档的内置段落指令各不相同。
- **`note` 与 `place` 会进提示词**：不要在里面写不该让模型知道的事（剧透、内部编号），
  它们每段都在。
- **身高不要写死**：身高由角色快照注入，方案文案里写死会和她实际的身材数据打架。
- **改 `initial_prompt` 不要顺手改输出协议**：JSON 形状、`direction` 与
  `custom_directions` 的语义由程序解析，改了只会让服从率下降。
- **人物表的称呼必须唯一**：称呼或别称撞车会让说话人标记与音色串台，校验器报 error；
  重要角色超过 6 位会提示。
- **`tagged` 与 `literary` 不许混用**：`literary` 方案的作者正文（初始提示、身份背景、
  章节备注、插入文本）里出现 `@说话人@` 会被报 error。
- **长字段会被提示**：主角背景 >300 字、人物背景 >200 字、作用 / 说话方式 >60 字各
  一条 warning，因为这些字段每段或每次出场都要发送。
- **温度、窗口、块大小不在方案里**：温度与压缩块大小是程序常量；对话历史窗口存在
  `data/user/dungeon_settings.json` 的 `story_recent_count`（2~200），界面上没有出口，
  只能手改这个文件。同一方案在所有玩家机器上的提示词结构一致。
- **交付前自检**：`python tests/run_checks.py check_scenario_schema check_scenario_admission`
  跑字段契约；`python scripts/scenario_validate.py` 批量跑方案诊断。
